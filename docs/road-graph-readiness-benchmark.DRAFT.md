# Read-only production readiness notes — no execution authorization

## Shadow-table swap and foreign keys

The loader uses `TRUNCATE public.road_edges, public.road_nodes RESTART IDENTITY CASCADE`. Its `road_edges.source_node_id` and `target_node_id` reference `road_nodes.id`; `road_edges.import_run_id` references `import_runs.id` (confirm exact FK names and ON DELETE actions from the deployed catalog before any plan). A rename-only swap does **not** redirect foreign keys: PostgreSQL FKs bind to table object OIDs, not textual names. Replacing `road_nodes` while keeping old `road_edges` (or vice versa) breaks referential consistency; downstream routing tables, views, functions, and privileges may continue referring to the old objects. Cascading deletes/truncates can also erase unrelated dependent data. Audit every referencing FK and its `ON DELETE` rule, plus sequences, indexes, RLS, grants, functions, views, materialized views, and routing references. Do not assume `ON DELETE CASCADE` is identical to `TRUNCATE CASCADE`: they are separate mechanisms. A shadow strategy needs a proven coordinated generation-based cutover or fully rehearsed transactional constraint/dependency rewiring; **do not recommend a rename-only swap**.

## Benchmark plan (restored copy only)

1. Obtain an approved encrypted logical dump or provider-managed snapshot/PITR of the production database including schemas, extensions, sequences, graph tables, import metadata, component stats and referencing objects. Restore it into a **separate isolated project** with no production secrets, outbound jobs, webhooks, or external consumers; use matching PostgreSQL/PostGIS/pgRouting versions and representative compute/storage. Never restore over production.
2. Verify schema/FK counts, graph edge baseline (338,188), node count, sample routing responses, table sizes, index definitions, and source-data checksums. Keep the original restored state as a rollback baseline.
3. Benchmark candidate atomic script on a disposable clone of that restored environment; stage files and run under controlled maintenance-like conditions. Collect durations for COPY, TRUNCATE, node/edge INSERT, pgr_connectedComponents, node/edge component updates, projected-coordinate update, stats rebuild, validation and COMMIT separately. Also capture peak RAM, CPU, I/O, WAL bytes, temp spill, storage headroom, locks and blocked-query duration, autovacuum/dead tuples, and p50/p95/p99 routing latency under concurrent representative read load.
4. Fault-inject failure immediately after edge insert, after component rebuild and before completion marker; verify entire transaction rolls back, prior graph and import metadata remain consistent, and routing recovers. Rehearse backup restore and record measured recovery time and data-loss exposure. Measure how long blocked readers wait and whether statement/lock timeouts are respected.
5. Proposed release gates (to agree with operator before testing): zero missing or inconsistent projected coordinates; all edge endpoints and FK references valid; exactly one primary component when eligible graph nonempty; stats counts equal node assignments; no incomplete import marked completed; matching expected edge count and route-sample outcomes; successful rollback at every injected failure; backup restore proven; disk/WAL headroom >= 2x measured peak temporary growth; p95 routing latency <= 2x pretest baseline during cutover and back to baseline afterward; lock/reader interruption <= 60 seconds; full maintenance work <= 15 minutes, including 2x safety margin against the measured p95 rehearsal time. If these cannot be met, redesign cutover or schedule a longer explicitly approved window rather than waive checks.

These are proposed gates, not measured results or permission to execute.
